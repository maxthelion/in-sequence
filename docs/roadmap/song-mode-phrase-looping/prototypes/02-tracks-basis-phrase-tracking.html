Tracks UI Basis-Phrase Tracking — Wireframe

Story 5: Tracks UI basis phrase follows free-play phrase navigation • Balsamiq-style, not a production proposal

Interaction budget: The Tracks UI basis phrase updates automatically — zero extra interactions required from the performer.
  1. When a phrase is queued (transport story 2), the Tracks UI immediately previews the queued phrase
  2. When a phrase switches (story 3 end-of-cycle or story 4 immediate), the Tracks UI confirms the new active phrase

The "Basis:" banner and the "editing:" label in the grid header both update when a phrase is queued or switched. This reflects Story 5: edits always land in the phrase the performer is hearing (or about to hear).

Static three-state reference — what the basis-phrase banner shows in each state

These are snapshot views. The interactive demo above shows transitions.

State 1 — Playing, nothing queued
Basis: Phrase A (Intro)
  • Basis phrase = currently playing phrase
  • Grid shows Pattern A data for all tracks
  • Edits write to Phrase A
State 2 — Playing A, queued C (preview)
Basis: Phrase C (Chorus) queued preview
  • Basis phrase switches to queued phrase immediately on queue
  • Grid shows Pattern C data — performer previews what they're queuing into
  • Edits made now write to Phrase C
  • Transport bar still shows "Now: Phrase A" — audio has not changed yet
State 3 — After switch to C (playing)
Basis: Phrase C (Chorus)
  • Basis phrase = Phrase C (now playing)
  • Banner returns to blue (active-playing) from amber (queued-preview)
  • Grid shows Pattern C — same data as state 2, but confirmed as active
Architecture note (from existing-state.md): Today the Tracks UI basis phrase reads session.store.selectedPhraseID in free mode. Story 5 requires the basis phrase to follow the queued phrase as well as the playing phrase. This means either: (a) a new published property on EngineController (e.g. basisPhraseID) that views prefer over selectedPhraseID when in free mode, or (b) a mutation to SequencerDocumentSession that persists the queued-phrase selection back to selectedPhraseID. Option (a) keeps live-performance state separate from document state and is the safer choice. The implementation loop should decide before writing code.
Open questions surfaced by this wireframe
  1. Queue triggers basis-phrase preview immediately? The wireframe answers "yes" — the performer wants to see and potentially edit the upcoming phrase the moment they queue it. Confirm this is correct with user.
  2. What happens to un-saved edits on basis-phrase switch? If the performer has edited Phrase C (the queued basis) and then cancels the queue, those edits are already written to the canonical phrase model (no staging layer today). The UX should warn or prevent this. This interacts with the Phrase Features story-4 staging gap.
  3. Basis-phrase banner visibility when not in free-play mode? In song mode (auto-cycle), the basis phrase would follow the engine's auto-derived phrase index. The banner design should remain consistent; confirm the same banner appears in both modes.
  4. Does cuing reset the grid scroll position? If Phrase C has more bars than Phrase A, the grid would need to resize or scroll. The prototype does not address this; it assumes all phrases have the same bar count for simplicity.
