  • Different: autoslice controls live in SETUP only MOVED; perform mode gets slice-movement macros (rotary, per the house control grammar).
  • Kit-style lanes rejected (Max): the default sequence is the identity diagonal — one active step per lane wastes N lanes of vertical space on zero information.
  • Instead: a single slice-sequence row — position = step, value = slice. The diagonal reads flat ("S1 S2 S3 …"); deviations render solid so the remix is what the eye sees. Cells reuse the existing sliceLabel/value-cell grammar.
  • Structurally this is a step-order map applied to slices — the machinery (and its pending-toggle quantise behavior) already exists; per-slice velocity/chance stay as layers on the same row, not extra lanes.
  • The three-process split (Max): (1) load/slice/apply = palette creation → SETUP; (2) slice sound/playback characteristics = part editing → dive into the slice (drum-part grammar; slice carries its defaults everywhere); (3) rearrange/copy steps = sequence editing → this row, with per-step overrides layered on slice defaults (Rytm sound-lock model).
  • Open design point — selection scope: on the sequence row a cell tap must be unambiguous between "this STEP" (edit what plays here: rotary row, copy/paste, locks) and "this SLICE" (edit the palette object everywhere it's used). Proposed: tap = step scope; tap the slice label / hold = slice scope, opening the slice editor like a drum-part dive-in. One grid, two signposted exits.

The one rule underneath all nine

Setup configures; Perform plays. If a control changes what a thing is (instrument, routing, macro assignment, slice points), it lives in Setup. If it changes what you hear next bar (pattern, mute, fill, part on/off, macro value), it lives in Perform — visible, quantisable, capturable.
