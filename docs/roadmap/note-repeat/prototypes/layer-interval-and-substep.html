1/16 interval — Layer Settings

Story 3 Story 4

The repeat interval is stored per track layer and persists when the performer navigates away. The segmented control surfaces all three named intervals in a single tap.

New model field: repeatInterval
Added to StepSequenceTrack. Enum: .off | .sixteenth | .thirtySecond | .sixtyFourth. Persisted via decodeIfPresent (defaults to .sixteenth). No phrase-layer grid needed — this is a scalar setting, not a per-step value.

Location proposal

The interval selector appears in the track layer settings panel — the same sheet reached from TracksMatrixView edit mode when the performer drills into a track. This is consistent with other per-track scalar settings (velocity, gate length).

Gap (existing-state report): StepSequenceTrack has no repeatInterval field today. The phrase-layer system (PhraseLayerDefinition.defaultSet) also has no repeat-interval entry. Both must be added.

1/16 interval (this tab)

One firing per step. No sub-step scheduling needed. The existing TickClock (1 tick = 1/16 step) is sufficient. This is the safe default and the lowest-risk implementation milestone.

Interaction budget

1 tap to change interval in layer settings. Setting takes effect immediately on next Note Repeat engage.

1/32 interval — Sub-step (2x per step)

Story 3 Story 4

At 1/32 the captured step fires twice inside the 1/16 tick window. The diagram shows the intended musical behaviour: two equally-spaced retriggers, each at half-step offset.

Architecture risk (existing-state report): TickClock fires once per 1/16 step. There is no intra-step scheduling mechanism. One of three approaches is required:
  • Run TickClock at 64 steps/bar with the main sequencer advancing every N ticks (lowest friction)
  • Add a secondary intra-step timer fired only when sub-step repeat is active
  • Dispatch multiple note events from within a single Executor.tick call with sample-accurate offsets
This is the key open architecture question to resolve before spec can be finalized.

Thread-safety requirement

Live interval changes from the UI (main thread) must reach the engine (clock callback queue) via CommandQueue or withStateLock. The existing pattern for live macro overrides is the right analogy.

Visual affordance for sub-step options

The "sub" badge on 1/32 and 1/64 options signals to the designer/implementer that these values require extra engine work. The badge disappears once sub-step scheduling exists — it is a prototype-only annotation, not a production UI element.

Interaction budget

1 tap in the interval selector. No additional confirmation needed. Budget: 1 tap.

1/64 interval — Sub-step (4x per step)

Story 3 Story 4

At 1/64 the captured step fires four times inside a single 1/16 tick. At 128 bpm, that is approximately one retrigger every 29 ms — well within audible range and the fastest option exposed to the performer.

Architecture risk (existing-state report): Four firings per tick compounds the sub-step scheduling problem from the 1/32 case. Additionally:
  • Gate-length clamping is required: if the step's gate is longer than 29 ms the engine must truncate each firing to avoid overlap
  • MIDI note-off timing at 29 ms granularity may expose latency in MidiOut's pending-noteoff queue
  • At very high BPM (>180) the 1/64 window drops below 15 ms, potentially within audio buffer latency; this edge case should be noted in the spec

Why show all three in one control

Placing 1/16, 1/32, and 1/64 as a segmented choice (not a numeric input) keeps the performer's decision cognitive-load-free. Three options is the right upper bound for a live control.

Persistence note

The selected interval for each track is stored in StepSequenceTrack.repeatInterval and survives document save/load. The interval is not per-scene or per-phrase-bar — it is a track-level default. If per-scene variation is needed later, it can be added as a phrase-layer target (analogous to fill-flag), but that is out of scope for the first implementation.
