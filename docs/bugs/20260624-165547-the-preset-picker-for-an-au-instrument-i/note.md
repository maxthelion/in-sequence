Status: RESOLVED — NARROWED (uncommitted, branch audio-routing-cleanup) — Root cause hypothesis: the AU shown (Arturia Analog Lab V) vends some factory presets as MIDI program-change slots named literally "ProgramChange1..N". The picker set `au.currentPreset = preset` only, which (for those slots) does NOT audibly switch the patch — they switch on a real MIDI Program Change. The fix is now SAFE-BY-CONSTRUCTION: `AudioInstrumentHost.loadPreset` sends an immediate MIDI Program Change (0xC0 + program number) via `scheduleMIDIEventBlock` ONLY when (a) the descriptor is `.factory`, (b) `scheduleMIDIEventBlock != nil`, and (c) the preset's NAME matches `^\s*ProgramChange\s*\d+\s*$` (case-insensitive). The program number is DERIVED FROM THE NAME (the AU's own declared program N), not from `preset.number` (which is just the factory-presets array index and would clamp/collide). All sent under `auMutationLock`. This means a NORMAL AU whose factory presets are real parameter-state ("Warm Pad", "Bright Lead") never gets a Program Change, so the common case where `currentPreset =` is authoritative cannot regress / double-switch. User presets keep the `currentPreset =` path. Star motif: changed to a checkmark in `AUPresetRowView` (kept). Tests: `programChangeBytes` status/number/clamp tests PLUS a name-parser/gate suite (`programNumberFromPresetName`) proving ProgramChangeN slots ARE recognised with the name-derived number (case-insensitive + whitespace) and — the key regression guard — that normal/near-miss names ("Warm Pad", "Bass 3", "Program Bank", "ProgramChange" with no number, "ProgramChange7a", "MyProgramChange7", "") return nil → NO Program Change. No live-AU `scheduleMIDIEventBlock` stub seam exists (the repo deliberately skips live AVAudioUnitMIDIInstrument lifecycle tests), so the decision is covered via the name-parser/gate seam, not via a live `loadPreset` call.
